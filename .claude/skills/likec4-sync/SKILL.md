Regenerate `model/generated/elements.c4` and `model/generated/relationships.c4`
from `@likec4` / `@likec4-rel` tags found in code comments across the repo.
This is an **agent-driven** operation: you read annotated source files
directly and author the generated DSL yourself, rather than running a
separate parser script.

**Write boundary — read this first:** you may only write inside
`model/generated/**`. Never write to `model/manual/**`, `model/views/**`, or
`model/specification.c4`. Those are hand-authored; you read them only to
resolve relationship target ids and to check which kinds/tags are declared.

## Steps

1. **Read the grammar.** Read `docs/likec4-annotations.md` in full. It is the
   single source of truth for the tag syntax — do not rely on a cached or
   assumed grammar, since it can change independently of this skill.

2. **Discover annotations.** Run:
   ```bash
   grep -rn "@likec4" --include='*' .
   ```
   scoped to the repo, excluding `model/`, `docs/`, and `.claude/` themselves
   (the grammar doc and this skill file both legitimately contain the
   literal tag strings as prose, not real annotations) and the usual
   `node_modules`/`.git`/`dist` noise. For each matched file, **Read the
   whole file** (not just the matched line) so you can capture the full
   doc comment block, the nearest following symbol name, and accurate line
   numbers.

3. **Parse each comment block** into one element plus zero or more outgoing
   relationships, per the grammar doc. Track `sourceFile`/`sourceLine` for
   every element and relationship — these become trailing `// file:line`
   comments in the generated DSL for traceability.

4. **Resolve relationship targets.** Build the set of all ids declared
   anywhere under `model/**.c4` (generated and manual) by reading
   `model/specification.c4`, everything under `model/manual/`, and the
   elements you just parsed in step 3. Any `@likec4-rel` target id not in
   this combined set is **dangling**. LikeC4 does not allow relationships to
   reference an undeclared id — `likec4 validate` hard-fails on one, not
   just warns — so you must **omit that relationship line** from the
   generated output rather than emit it. Flag it clearly in your final
   report instead, so the omission isn't silent: either the target id is a
   typo, or it's a legitimate external system that still needs a hand-authored
   declaration added to `model/manual/`.

5. **Check kinds against the specification.** If an annotation uses an
   element `kind` or relationship `kind:` not declared in
   `model/specification.c4`, do not invent it — flag it in your report and
   skip emitting that one tag's effect (emit the element/relationship
   without the unknown kind rather than dropping it entirely, unless that's
   not possible, in which case skip it and say so).

6. **Rewrite the generated files wholesale.** Overwrite
   `model/generated/elements.c4` and `model/generated/relationships.c4` in
   full — do not try to merge into their previous contents, there is nothing
   there worth preserving since you own the whole file. Keep the leading
   `// AI-managed — fully regenerated...` header comment. Format:

   ```
   // AI-managed — fully regenerated by the likec4-sync skill on every run.
   // Do not hand-edit; your changes will be overwritten on the next sync.
   model {
     orders-service = container 'Orders Service' {
       technology 'Node.js, Express'
       description '...'
     }
   }
   ```

   ```
   // AI-managed — fully regenerated by the likec4-sync skill on every run.
   // Do not hand-edit; your changes will be overwritten on the next sync.
   model {
     orders-service -> payments-service "charges the customer's card" 'REST/HTTPS' // examples/annotated/orders-service.ts:6
   }
   ```

7. **Validate.** Run `npx likec4 validate`. If it fails, leave the files you
   just wrote in place (the user can inspect `git diff`) and report the raw
   validator error — do not attempt more than one self-correction pass, and
   never silently discard your changes to "fix" a failure.

8. **Report a summary** covering:
   - New elements discovered (id, kind, `file:line`)
   - Elements removed from `model/generated/*` because their annotation is
     gone (call these out explicitly as **orphaned** — the underlying code
     may have moved/renamed rather than been deleted, so don't phrase this
     as a deletion)
   - Relationships added/removed
   - Dangling relationship targets (from step 4)
   - Annotations using an undeclared kind (from step 5)
   - `likec4 validate` pass/fail
   - An explicit confirmation that `model/manual/**` and `model/views/**`
     were not touched
   - Do **not** commit anything — leave the working tree diff for the user
     to review.

## Guardrails

- Read `docs/likec4-annotations.md` fresh every run; don't assume you recall
  it correctly from a prior conversation turn.
- Never write outside `model/generated/**`.
- A dangling relationship target or undeclared kind means omitting that one
  line from generated output (so the rest of the model still validates) —
  but always say so in the report. Never drop it from the output *and* the
  report; that's the silent failure mode to avoid.
- The operation should be idempotent — running it twice with no code changes
  produces identical generated files.
- If `grep` finds zero annotations, say so plainly and still run
  `npx likec4 validate` against the (now-empty) generated files so the model
  is left in a valid state.
